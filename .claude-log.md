### KRITIEK

**1. SSRF via `/api/thumb` — ongeauthenticeerd, geen URL-validatie**
`main.py:1889-1941` (`get_thumb`), sinks op `1913` en `1919`.
- Het endpoint heeft **geen auth-dependency** (geen `Depends(...)`) en accepteert een vrije `url`-query-parameter die direct in `urllib.request.urlopen(...)` gaat.
- Extra verergering: `ssl_ctx.check_hostname = False` + `ssl_ctx.verify_mode = ssl.CERT_NONE` (`1904-1905`) — TLS-verificatie volledig uit.
- `urllib` volgt HTTP-redirects en ondersteunt `file://` schemes.

Misbruikscenario:
- `GET /api/thumb?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/` → cloud metadata / IAM-credentials ophalen (afhankelijk van hosting; op AWS-achtige omgevingen kritiek).

## Security audit — frontend `static/` (XSS, client-side trust, exposed data)

Scope: `scan.js`, `beheer.js`, `catalogus.js`, `app.js` and the `.html` files. Read-only, nothing changed. The core issue is systemic: there is one `_esc()` helper in `scan.js` (lines 880-884) used *only* in the chat renderer (`laadBerichten`/`verstuurBericht`). Almost every other `innerHTML` template-literal interpolates server/AI/user-controlled data **without escaping**.

### How data becomes attacker-controlled
- **`ai_label` / `ai_detail`**: AI-generated from an uploaded photo. Any scanner can upload an image crafted so the model returns a label/detail containing `&lt;img src=x onerror=...&gt;`. This is stored and later rendered in admin/company/public screens → **stored XSS across trust boundaries**.
- **organisatie / username / bedrijf naam / gemeente / category / manual_note**: set by users/admins on creation or edit; rendered raw in other users' screens.

## Findings (sorted by severity)

### CRITICAL

**C1 — Stored XSS via `ai_label`/`ai_detail`/`bedrijf_naam` in the superadmin gemeente-dashboard**
`beheer.js:413-421` (`openGemeenteDashboard` → `itemRows`): `${it.ai_label}`, `${it.category}`, `${it.bedrijf_naam}` interpolated into `innerHTML`. A scanner in any gemeente can plant a payload via a scanned item; it executes in the **superadmin** browser, whose token can create/delete users, impersonate anyone, and change roles. Full platform takeover.
Fix: escape all interpolated fields (add/import an `_esc()` and wrap every field), or build nodes with `textContent`.

**C2 — Stored XSS via `username`, `gemeente`, `bedrijf.naam` in the admin user-management list**
`beheer.js:185-215` (`loadUsers`): `${u.username}`, `${u.gemeente}`, and in the bedrijf-select `${b.naam}` + `${b.gemeente}` (line 210) all raw in `innerHTML`. `u.username` is attacker-set at registration/creation. Executes in superadmin context. Note line 196 also injects `'${u.username}'` inside an inline `onclick` — a username with a quote/`&lt;/script&gt;`-style payload breaks out of both the JS string and the HTML attribute.
Fix: escape fields; never build `onclick` with raw string data — use `data-` attributes + `addEventListener`, or at minimum `_esc` + attribute-safe encoding.

# Security-audit — authenticatie &amp; autorisatie (CIRQO / app.cirqo.nl)

Onderzocht: `main.py`, `auth.py`, plus geverifieerd in `database.py`. Bevindingen gesorteerd op severity.

## KRITIEK

### 1. Rol-escalatie via `PATCH /api/users/{id}/role` — gemeente-admin kan willekeurige user (of zichzelf) admin/bedrijf maken op elke gemeente
`main.py:1005-1020` (`change_user_role`) + `database.py:425` (`update_user_role`)
Beschermd met `require_admin` (dus ook een gewone gemeente-`admin`). Maar er is **geen gemeente-scope-check** en **geen check dat de admin de doelgebruiker mag beheren**. De enige beperkingen: doel mag geen `superadmin` zijn, en de nieuwe rol mag alleen `user/admin/bedrijf` zijn.
Misbruik: een gemeente-admin van gemeente X roept `PATCH /api/users/{willekeurig_id}/role` aan met `role=admin` op een user in gemeente Y — of op zichzelf om `bedrijf_id` van een ander bedrijf te koppelen (`bedrijf_id` wordt ongefilterd doorgezet naar de DB, `database.py:427-429`). Vergelijk met `delete_user` (`main.py:997`) dat wél `target["gemeente"] != admin["gemeente"]` checkt — hier ontbreekt die check volledig.
Fix: voeg `if admin["role"] == "admin"` toe: (a) doel moet in eigen gemeente zitten, (b) `role` beperken tot `user`/`admin`, (c) `bedrijf_id` alleen toestaan voor bedrijven in eigen gemeente. Overweeg rol-wijziging naar `require_superadmin`.

### 2. Broken access control op items: iedere ingelogde user kan elk item wijzigen/verwijderen (IDOR)
`main.py:1619-1640` (`update_item`, `delete_item`)
Beide gebruiken `Depends(get_current_user)` en checken alleen dat het item bestaat (`db.get_item(item_id)`), niet wie de eigenaar is of welke gemeente. `db.update_item`/`db.delete_item` (`database.py:525, 638`) doen `WHERE id = %s` zonder eigenaarschap.
Misbruik: een gewone scanner in gemeente A doet `DELETE /api/items/999` of `PATCH /api/items/999` op een item van een andere gebruiker/gemeente en wist of vervalst het (categorie/opmerking). Volledige cross-tenant data-manipulatie.
Fix: controleer `item["uploaded_by"] == user["id"]` OF admin met matchende gemeente, voordat je muteert.

### 3. Bericht-toegang IDOR via `bedrijf_id`-vergelijking met None
`main.py:1361-1372` (`get_berichten`) en `1375-1390` (`stuur_bericht`)
De check `is_bedrijf = user.get("bedrijf_id") == info.get("bedrijf_id")`. Voor een aanbieding zonder gekoppeld bedrijf, of voor een user zonder `bedrijf_id`, is dit `None == None` → **True**. Belangrijker: elke `user` die niet de aanbieder is maar wel `bedrijf_id` toevallig gelijk heeft, of de aanbieder-check `aangeboden_door == user["id"]` — aangezien `aangeboden_door` bij Firestore-import `NULL` kan zijn (`database.py:824` accepteert `user_id=None`; import-flows zetten soms geen `aangeboden_door`), kan `info.get("aangeboden_door")` `None` zijn. Een aanvaller met `bedrijf_id=None` in zijn token krijgt bij een aanbieding met `bedrijf_id=None` toegang tot de chat.
Misbruik: gebruiker leest of plaatst berichten in gesprekken tussen andere partijen door aanbieding-ids te itereren.
Fix: expliciete guard `if info.get("bedrijf_id") is None or user.get("bedrijf_id") is None: is_bedrijf = False`, en idem voor `aangeboden_door`.

### 4. `PATCH /api/aanbiedingen/{id}/status` — status van elke aanbieding wijzigbaar door elke ingelogde user
`main.py:1606-1616` (`update_aanbieding_status_admin`)
Ondanks de functienaam met `_admin` is de dependency `Depends(get_current_user)` — geen rol- of eigenaarschapscontrole. Elke user kan de status van een willekeurige aanbieding op `open/ophalen/niet_nodig` zetten.
Misbruik: concurrent-bedrijf zet aanbiedingen van anderen op `niet_nodig`, of manipuleert workflow-status massaal via id-iteratie.
Fix: check dat user aanbieder, betrokken bedrijf, of admin is (zoals bij berichten). Of maak het `require_admin`.

### 5. `POST /api/aanbiedingen` en `/bulk` — aanbieden namens/aan willekeurige items en bedrijven
`main.py:1166-1197`, `1200-1241` (`create_aanbieding`, `create_aanbiedingen_bulk`)
`Depends(get_current_user)`, geen check dat `item_id` van de user is, noch dat de user aan `bedrijf_id` mag aanbieden. `db.create_aanbieding` (`database.py:821`) doet blind insert.
Misbruik: user koppelt andermans items aan willekeurige bedrijven en triggert push-notificaties (spam) naar die bedrijven (`_stuur_bedrijf_push`). Ook bruikbaar voor enumeratie.
Fix: verifieer `item.uploaded_by == user["id"]` (of admin), en dat het bedrijf in de gemeente-scope valt.

## HOOG

### 6. Zwakke wachtwoord-hashing (single-round HMAC-SHA256, geen KDF)
`auth.py:13-25`
Wachtwoorden worden opgeslagen als `salt$hmac_sha256(salt, wachtwoord)` — één ronde, geen bcrypt/scrypt/argon2/PBKDF2. Bij een DB-lek zijn wachtwoorden extreem snel te brute-forcen (miljarden/sec op GPU). Salt is wel per-user (goed), en `compare_digest` wordt gebruikt (goed).
Fix: migreer naar `bcrypt`/`argon2`. Ondersteun beide tijdelijk en re-hash bij login.

### 7. Hardcoded / voorspelbare `SECRET_KEY` fallback + extreem lange tokengeldigheid, geen intrekking
`auth.py:8-10`
`SECRET_KEY = os.environ.get("SECRET_KEY", "verander-dit-in-productie-naar-iets-geheims")`. Als de env-var niet gezet is, is de JWT-signing-key publiek bekend (staat in de repo) → **iedereen kan geldige tokens voor role=superadmin smeden**. Bovendien `TOKEN_EXPIRE_DAYS = 365`: tokens leven een jaar, en er is geen server-side intrekking. Rol/gemeente/bedrijf_id komen puur uit het token (`main.py:38-45`), dus een gepromote of gedegradeerde user houdt zijn oude rechten een jaar lang.
Misbruik: (a) draait de app zonder `SECRET_KEY`, dan volledige overname. (b) Zelfs met key: gecompromitteerde/gestolen token blijft een jaar bruikbaar, verwijderde user blijft ingelogd.
Fix: fail-fast als `SECRET_KEY` ontbreekt (geen fallback). Verkort expiry drastisch + refresh-tokens. Overweeg een token-versie/`iat`-check tegen DB voor intrekking.

### 8. Impersonatie geeft een normaal, langlevend token zonder markering
`main.py:821-840` (`impersonate`)
Toegang is correct beperkt tot `superadmin` (goed). Maar het uitgegeven token is niet te onderscheiden van een echt login-token: geen `impersonated_by`-claim, geen kortere expiry (dus 1 jaar), geen audit-log. Een superadmin kan als elk account handelen zonder spoor; en het impersonatie-token overleeft het intrekken van superadmin-rechten.
Fix: voeg `act`/`impersonated_by`-claim toe, korte expiry, en log de actie.

### 9. Bedrijf-token-login: token = `meld_token`, langlevend en in beheer-lijsten blootgesteld
`main.py:504-526` (`login_met_token`) + `database.py:814`
`GET /api/auth/bedrijf-token/{token}` geeft een volwaardig bedrijf-JWT terug aan wie de `meld_token` (een UUID) kent. Deze `meld_token` wordt óók teruggegeven in `get_aanbiedingen_voor_beheer` (`database.py:879, 890`) en zit in meld-links. Een UUID is niet raadbaar, maar het is een permanente bearer-credential zonder rotatie of expiry — wie de link onderschept (logs, referer, doorgestuurde e-mail) logt permanent in als het bedrijf.
Fix: maak deze links kortlevend/eenmalig, of wissel meteen in voor een sessietoken en roteer `meld_token`.

## MIDDEL

### 10. Firebase-login kent rol toe op basis van Firestore-veld en e-mail-matching — ongewenste rol/koppeling mogelijk
`main.py:550-618` (`firebase_login`)
Rol `admin` wordt gezet als het Firestore `users3`-document `Administrator` truthy heeft (`main.py:583-584`). De `users3`-collectie en het e-mail→bedrijf-matchen (`get_bedrijf_by_email`, `main.py:590`) bepalen privileges. Wie in Firestore schrijfrechten heeft op `users3`, of wie een bedrijf-e-mail claimt (Firebase `email_verified` wordt hier **niet** gecontroleerd), kan zo `admin`- of `bedrijf`-rechten krijgen. `upsert_firebase_user` matcht bovendien op `email OR username` (`database.py:307`) — een nieuw Firebase-account met e-mail gelijk aan een bestaande `username` kapt dat bestaande account.
Fix: controleer `decoded.get("email_verified")`; ken rollen niet toe op basis van niet-geverifieerde e-mail; verifieer de `users3`-`Administrator`-bron; match niet op `username` bij Firebase-koppeling.

### 11. `POST /api/auth/request-reset` maakt automatisch Firebase-accounts aan + account-enumeratie
`main.py:843-884`
Voor elke bestaande Supabase-user zonder Firebase-account maakt dit endpoint een Firebase-account aan en zet `firebase_uid`/`email` op het bestaande record (`main.py:876-880`). Ongeauthenticeerd. Combineert account-enumeratie (timing/gedrag verschilt tussen bestaande en niet-bestaande e-mail) met ongewenste account-creatie en het overschrijven van het `email`-veld van een bestaand account. Geen rate-limiting.
Fix: rate-limit, maak geen accounts aan op basis van ongeauthenticeerde input, en zorg dat het antwoord/timing identiek is ongeacht of de e-mail bestaat.

### 12. `PATCH /api/users/{id}/password` — admin (gemeente) kan wachtwoord van elke user resetten, ook buiten eigen gemeente
`main.py:1040-1060` (`change_password`)
De check is alleen: `if user["role"] == "user" and user["id"] != user_id`. Dus een gemeente-`admin` (of `bedrijf`? nee, bedrijf heeft role 'bedrijf' — die valt ook nét niet onder 'user' en mag dus ook elke user resetten) kan het wachtwoord van **elke** user zetten, inclusief superadmin (`update_user_password` heeft geen superadmin-guard, `database.py:433`) en users in andere gemeenten. Firebase-wachtwoord wordt meegesynct.
Misbruik: gemeente-admin (of een 'bedrijf'-account) reset het wachtwoord van een superadmin → account-overname.
Fix: sta voor `admin` alleen users in eigen gemeente toe; blokkeer targeten van `superadmin`; sluit rol `bedrijf` uit van andermans wachtwoorden.

### 13. `POST /api/auth/sync-password` zet Supabase-wachtwoord op basis van Firebase-token zonder e-mail-verificatie
`main.py:887-910`
Verifieert het Firebase ID-token (goed), maar koppelt daarna op `firebase_uid` óf `email` (`main.py:904-906`) en overschrijft het Supabase-wachtwoord. Als een aanvaller een Firebase-account maakt met een e-mail die overeenkomt met een bestaand Supabase-account (zonder gekoppelde `firebase_uid`), kan hij via de e-mail-fallback het wachtwoord van dat account overschrijven. `email_verified` wordt niet gecheckt.
Fix: match alleen op `firebase_uid`; als je op e-mail matcht, eis `decoded["email_verified"] is True`.
